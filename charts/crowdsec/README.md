## Architecture

| Component | Workload | Role |
|-----------|----------|------|
| `lapi` | Deployment | Local API: receives alerts, stores decisions, serves bouncers. Stateless, backed by an **external PostgreSQL or MySQL database**. |
| `agent` | DaemonSet (or Deployment) | Log processor: reads logs, detects attacks, sends alerts to LAPI. |
| `appsec` | Deployment | Web Application Firewall component queried by bouncers. Disabled by default. |

Every pod uses the upstream image entrypoint, configured through environment variables and files mounted in `/etc/crowdsec`.
Agents and AppSec register to LAPI with a token generated by the chart (or with client certificates when [TLS](#tls) is enabled).

All resources are named `<release>-crowdsec-<component>` (or `<release>-<component>` if the release name contains `crowdsec`),
so several releases can live in the same namespace.

## Installing the chart

LAPI needs a database. Any PostgreSQL or MySQL works; in Kubernetes, an operator such as
[CloudNativePG](https://cloudnative-pg.io) is a convenient option:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: crowdsec-db
  namespace: crowdsec
spec:
  instances: 2
  storage:
    size: 5Gi
  bootstrap:
    initdb:
      database: crowdsec
      owner: crowdsec
```

CloudNativePG creates a `crowdsec-db-app` Secret (key `password`) and a `crowdsec-db-rw` Service.
Then install the chart:

```yaml
# crowdsec-values.yaml
lapi:
  database:
    type: postgresql
    host: crowdsec-db-rw
    existingSecret: crowdsec-db-app
agent:
  hub:
    collections:
      - crowdsecurity/nginx
  podLogs:
    - namespace: ingress-nginx
      pod: ingress-nginx-controller-*
      program: nginx
```

```sh
helm repo add crowdsec https://crowdsecurity.github.io/helm-charts
helm install crowdsec crowdsec/crowdsec -n crowdsec --create-namespace -f crowdsec-values.yaml
helm test crowdsec -n crowdsec
```

## Reading pod logs

`agent.podLogs` reads the container logs of matching pods on every node (`/var/log/containers/<pod>_<namespace>_*.log`),
and `program` selects the parsers to apply. Install the matching collection with `agent.hub.collections`.

Logs are expected in the CRI format (containerd, CRI-O). On nodes using Docker through cri-dockerd, use
`agent.acquisition` with `labels.type: docker`, and mount `/var/lib/docker/containers` with `agent.extraVolumes`/`agent.extraVolumeMounts`.

Any other [datasource](https://docs.crowdsec.net/docs/next/log_processor/data_sources/intro) can be added as-is to
`agent.acquisition`. Network datasources usually run better with `agent.kind: Deployment`, and `agent.extraPorts`
exposes their port on the container and the agent Service:

```yaml
agent:
  kind: Deployment
  podLogs: []
  extraPorts:
    - name: syslog
      port: 4242
      protocol: UDP
  acquisition:
    - source: syslog
      listen_addr: 0.0.0.0
      listen_port: 4242
      labels:
        type: syslog
```

## Hub items and custom files

Hub items are installed at startup from the `hub` lists of each component (`collections`, `parsers`, `scenarios`, ...).
Other entrypoint variables, such as `DISABLE_PARSERS`, can be set with `env`.

Every component accepts:

- `config`: settings merged into its `config.yaml.local`, on top of what the chart manages
  (database, auto-registration, credentials paths). Anything set here wins.
- `files`: any file under `/etc/crowdsec`, keyed by its relative path. Use `--set-file` to load them from disk.

```yaml
agent:
  files:
    parsers/s01-parse/my-parser.yaml: |
      ...
    scenarios/my-scenario.yaml: |
      ...
    simulation.yaml: |
      simulation: false
      exclusions:
        - crowdsecurity/ssh-bf
lapi:
  config:
    db_config:
      max_open_conns: 50
  files:
    profiles.yaml: |
      ...
    notifications/slack.yaml: |
      type: slack
      name: slack_default
      webhook: ${SLACK_WEBHOOK}  # environment variables are expanded
  env:
    - name: SLACK_WEBHOOK
      valueFrom:
        secretKeyRef: {name: slack, key: webhook}
```

```sh
helm upgrade crowdsec crowdsec/crowdsec --reuse-values \
  --set-file 'agent.files.scenarios/my-scenario\.yaml=./my-scenario.yaml'
```

Pods restart automatically when their configuration changes.

## Bouncers

Register a bouncer and get its API key:

```sh
kubectl -n crowdsec exec deploy/crowdsec-lapi -- cscli bouncers add my-bouncer
```

To use a predefined key instead, pass `BOUNCER_KEY_<name>` to LAPI, e.g. from a Secret:

```yaml
lapi:
  env:
    - name: BOUNCER_KEY_nginx
      valueFrom:
        secretKeyRef: {name: bouncer-keys, key: nginx}
```

Bouncers reach LAPI at `http://<release>-crowdsec-lapi.<namespace>.svc:8080` (`crowdsec-lapi` for a release named `crowdsec`).

## AppSec (WAF)

```yaml
appsec:
  enabled: true
```

This installs the virtual patching and generic rules collections and listens on port 7422 with the `crowdsecurity/appsec-default` config.
Point your bouncer (e.g. [ingress-nginx](https://docs.crowdsec.net/u/bouncers/ingress-nginx) or
[Traefik](https://github.com/maxlerebourg/crowdsec-bouncer-traefik-plugin)) to `http://<release>-crowdsec-appsec.<namespace>.svc:7422`.

When ingress controllers run as a DaemonSet, AppSec can run on every node too and keep the traffic node-local:

```yaml
appsec:
  enabled: true
  kind: DaemonSet
  service:
    internalTrafficPolicy: Local   # or trafficDistribution: PreferClose
```

Each additional listener in `appsec.acquisition` needs its port in `appsec.extraPorts` to be exposed on the Service.

Custom configurations and rules go in `appsec.files`:

```yaml
appsec:
  enabled: true
  hub:
    collections:
      - crowdsecurity/appsec-virtual-patching
      - crowdsecurity/appsec-crs
  acquisition:
    - source: appsec
      listen_addr: 0.0.0.0:7422
      path: /
      appsec_config: me/my-config
      labels:
        type: appsec
  files:
    appsec-configs/my-config.yaml: |
      name: me/my-config
      default_remediation: ban
      inband_rules:
        - crowdsecurity/base-config
        - crowdsecurity/vpatch-*
        - me/*
    appsec-rules/my-rule.yaml: |
      name: me/block-xmlrpc
      ...
```

## TLS

```yaml
tls:
  enabled: true
```

With TLS, LAPI serves HTTPS and agents/AppSec authenticate with client certificates instead of the registration token.
Certificates are issued by [cert-manager](https://cert-manager.io): from a self-signed CA dedicated to the release by default,
or from your own issuer with `tls.certManager.issuerRef`. The issuer must populate `ca.crt` in the certificate Secrets.

A client certificate for bouncers (OU `bouncer-ou`) is also issued in the `<release>-crowdsec-bouncer-tls` Secret.
Use `tls.certManager.secretTemplate` to add annotations to the Secrets, e.g. to replicate them to the bouncers' namespaces.

Without cert-manager, set `tls.certManager.enabled: false` and provide `tls.existingSecrets.lapi` and `tls.existingSecrets.agent`
(each with `tls.crt`, `tls.key` and `ca.crt`). The [hack/tls](../../hack/tls) scripts show how to create them.

## Central API and Console

LAPI connects to the CrowdSec Central API by default (community blocklist, Console). A Helm hook Job registers the instance
once and stores the credentials in the `<release>-crowdsec-capi-credentials` Secret, shared by all replicas.
This Secret is kept on uninstall so that reinstalling keeps the same identity; you can also provide your own with
`lapi.onlineAPI.existingSecret`. Set `lapi.onlineAPI.enabled: false` for an offline setup.

To enroll in the [Console](https://app.crowdsec.net):

```yaml
lapi:
  console:
    enrollKey: <key>      # or `enrollKey` in auth.existingSecret
    instanceName: my-cluster
    tags: [k8s]
```

Console sharing options go in `lapi.files["console.yaml"]`.

## High availability

LAPI is stateless, so it scales like any Deployment:

```yaml
lapi:
  replicas: 2
  podDisruptionBudget:
    enabled: true
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: ScheduleAnyway
      labelSelector:
        matchLabels:
          app.kubernetes.io/component: lapi
```

All LAPI replicas share a single local machine (`<release>-crowdsec-lapi`, used by `cscli` in the pods), whose
password is derived from `csLapiSecret`. Each agent and AppSec container start is a separate machine (registered with the token, or created by LAPI from the
client certificate with TLS), which unregisters itself when it stops (`api.client.unregister_on_exit`, can be disabled
in `agent.config` / `appsec.config`).
LAPI deletes the machines left behind (removed pods, OOM kills, node loss) once they have sent no heartbeat for
2 hours and own no alerts (`lapi.config.db_config.flush.agents_autodelete`).

## GitOps (ArgoCD, Flux)

The chart generates the registration token and the LAPI JWT secret, and reuses them across upgrades by looking up the existing Secret.
Tools that render templates without cluster access (ArgoCD, `helm template`) would regenerate them on every sync, so provide them instead:

```sh
kubectl -n crowdsec create secret generic crowdsec-auth \
  --from-literal=registrationToken=$(openssl rand -hex 24) \
  --from-literal=csLapiSecret=$(openssl rand -hex 32)
```

```yaml
auth:
  existingSecret: crowdsec-auth
```

For the same reason, set `lapi.onlineAPI.existingSecret` if your tool does not run Helm hooks.

## Agents with an external LAPI

Agents can report to a LAPI deployed elsewhere (another release, namespace or cluster):

```yaml
lapi:
  enabled: false
  externalURL: http://crowdsec-lapi.crowdsec.svc:8080
auth:
  existingSecret: crowdsec-auth   # holding the registrationToken of that LAPI
agent:
  podLogs: [...]
```

Only the `registrationToken` key of `auth.existingSecret` is used in this mode. On the external LAPI:

- `api.server.auto_registration` must be enabled with the same token, and allow the agents' source IPs in `allowed_ranges`
  (behind NAT, these are the node or egress IPs);
- every agent pod start creates a new machine, so set `db_config.flush.agents_autodelete` to clean up the ones that
  could not unregister, as this chart does for its own LAPI:
  ```yaml
  db_config:
    flush:
      agents_autodelete:
        login_password: 2h
        cert: 2h
  ```
- with TLS, set `tls.certManager.issuerRef` to an issuer trusted by that LAPI, which must accept the `agent-ou` OU.

## Exposing LAPI or AppSec outside the cluster

Services accept fixed node ports by port name and any extra Service spec field:

```yaml
lapi:
  service:
    type: LoadBalancer
    nodePorts:
      lapi: 30080
    extraSpec:
      externalTrafficPolicy: Local       # keep client IPs, checked by auto-registration
      loadBalancerSourceRanges: [203.0.113.0/24]
```

Without `externalTrafficPolicy: Local`, LAPI sees node IPs instead of client IPs: agents outside the cluster would then be
accepted or refused by `auto_registration.allowed_ranges` based on the node address.

## Security defaults

Every pod uses the `RuntimeDefault` seccomp profile and runs without a service account token.
Helper containers (LAPI wait/registration, Central API registration Job, `helm test` pods) run as `nobody` with a read-only
root filesystem and no capabilities (`helperContainers`). User namespaces can be enabled per component with `hostUsers: false`
on runtimes that support them; the agent may then be unable to read host logs.

The CrowdSec containers themselves still run as root: notification plugins switch users, and the agent reads host logs.

Outbound destinations are listed in the CrowdSec [network management](https://docs.crowdsec.net/docs/next/configuration/network_management)
documentation. In this chart:

- LAPI pods and the Central API registration Job reach the Central API (`api.crowdsec.net`, `blocklists.api.crowdsec.net`,
  `papi.api.crowdsec.net`), and LAPI pods reach the database. Only the Job needs the Kubernetes API.
- Agent and AppSec pods download hub items at startup (`cdn-hub.crowdsec.net`, `hub-data.crowdsec.net`, `version.crowdsec.net`)
  and reach LAPI on port 8080.

## Labels and annotations

`commonLabels` and `commonAnnotations` are added to every resource created by the chart, including the Secrets
issued by cert-manager and the Central API credentials Secret created by the registration Job.
Pods get `commonLabels`, plus `podLabels`/`podAnnotations` (global, then per component, which take precedence).
Most resources also accept their own annotations: `<component>.annotations` (workloads), `<component>.service.annotations`, `lapi.ingress.annotations`.

`extraObjects` deploys additional manifests with the release (e.g. an ExternalSecret providing the database password).
For changes the values do not cover, use a [post-renderer](https://helm.sh/docs/topics/advanced/#post-rendering) such as kustomize
rather than forking the chart.
